探索定位与工具运用

改代码前先搜、先读、先定位——用对工具组合少盲改，对应 A3 上下文与工具使用能力。
A3 上下文与工具使用能力
核心一句话：先看懂，再动手。 不读就改是返工头号来源。A3 只量两件事——探索占比（explore_ratio）和工具多样性（distinct_tools）；先 Grep/Glob/Read 摸清影响面再改，比直接动手准、还省 token。

1. 为什么这项重要

盲改的代价是改错地方、漏改调用点。A3 量的是动手前有没有先探索再编辑、工具箱够不够宽。最隐蔽的两点：explore_ratio 满分线 0.65——探索调用得占探索+编辑的约三分之二才满分，不是"读一下就行"；distinct_tools 的 k=24 很大，常用 4-5 个工具只拿十几分，得用上一打以上不同工具才到中段。还有个反直觉点：Bash 里敲 grep/rg/find/tree 这些 shell 探索命令也计入 explore_calls——不只 Read/Grep 工具调用，shell 命令那路是叠加的。

2. 反面 vs 正面

✗ 不看就改 "把登录逻辑改成 JWT。"——没让它先看现在怎么实现的、有哪些调用方，直接改，结果漏改了三处调用点。
✓ 先探索后编辑 "先 Grep 找出所有 auth 相关文件和调用点，Glob 定位，Read 读关键片段；报告 1.当前实现 2.谁调用了它 3.改动波及哪里；我确认后你再动手改。"

3. 照抄：先探索后编辑 prompt 骨架

把"先看懂"落成一句可复用的指令——同时示范了 Grep/Glob/Read 的工具组合多样性。粘进对话，按提示填：

# 先探索后编辑骨架（粘进对话，按符号/功能填）
要改的符号/功能：____
1. Grep 搜所有引用 ____ 的位置（带行号 -n）
2. Glob 定位相关文件（如 **/*.py、src/**/*.ts）
3. Read 读关键片段（用 offset/limit 只读相关段，别整文件倒进来）
4. 报告：① 当前实现  ② 调用方与影响面  ③ 改动会波及哪些地方
我确认后你再动手改，不要先改、不要顺手改别的。

4. 精准 grep vs 倒整文件

找一处符号，别把整个大文件读进上下文——撑爆工作记忆、费 token。先定位行号，再只读那一段：

✗ 倒整文件 Read 整个 2000 行的 score_session.py 找 classify_rm_command 在哪——上下文塞进一大半文件，后续每轮都背着它。
✓ 精准定位 Grep -n "classify_rm_command" mvp/score_session.py 拿到行号（比如 :262），再 Read offset=255 limit=40 只读那一段。

精准 grep 同时抬 explore_ratio（少倒整文件）和工具多样性（Grep+Read+offset/limit 组合）；也比 Read 整文件少塞上下文——缓存与输出维度见成本模块。A3 口径与公式见第 5 节。

5. 这动的是哪个分·A3

公式 a3 = 0.6·diversity_score + 0.4·explore_score，A3 ∈ L1、层权重 0.25。explore_score = clamp(explore_ratio / 0.65 · 100)，explore_ratio = explore_calls / (explore_calls + edit_calls)（denom=0 回退 0）；满分线 0.65——0.40 旧线只 ≈62、0.65 才满分、全探索无编辑 clamp 封顶 100，从 0.40 提到 0.65 净增约 15 分。

diversity_score = _dim_returns(distinct_tools, 24)，_dim_returns(n,k)=100·n/(n+k)：n=1≈4、n=6≈20、n=12≈33、n=24→50（中段）、n=90 才≈79。天花板 100；只用 1 个工具 + 全编辑的理论下限 ≈2.4（0.6·4+0.4·0）；explore_ratio=0.65 配 n=24→70、n=48→80、n=90→87。A3 全程可测无回退——三量都从 tool_use 事件直接数（不像 A1/A2 有 prompts_not_measurable 分支）；内部量跑 python mvp/score_session.py PATH.jsonl 看 A3 证据卡。

评分器数哪些工具

explore_calls 来自两路叠加（叠加不互斥，作用于不同调用）：工具名 ∈ EXPLORE_TOOLS（Read/Grep/Glob/LS/WebSearch/WebFetch/NotebookRead/Search 共 8 个）+ Bash 命令命中 SHELL_EXPLORE_RE（grep/rg/ls/find/cat/head/tail/tree/wc/awk 共 10 个）；edit_calls 来自 EDIT_TOOLS（Edit/Write/MultiEdit/NotebookEdit/Create/ApplyPatch/str_replace_editor 共 7 个）。

口径要点：distinct_tools = len(tool_use_counts) 按工具名去重、计入所有工具名，不只探索工具。抬 diversity 有两条路——扩探索工具（Read/Grep/Glob/LS/WebSearch/WebFetch + Bash 里 grep/rg/find/tree/wc）和用上不同编辑工具（Edit/Write/MultiEdit/NotebookEdit）。从 n=10 补到 n=24 的最小清单：探索侧补 NotebookRead/Search，编辑侧补 Create/ApplyPatch/str_replace_editor，再加规划 TodoWrite/TaskCreate/TaskList 与 Agent/Skill。n=48/90 实际还要靠 MCP 工具（mcp__*）堆名——公式值正确，但别当可达目标硬追。

子代理（Agent/Task）不在上述任一桶，计入 C1 不计入 A3（见 collab 模块）。

6. 广度搜索与套路复用

"扫全仓找 X"这类广度搜索派给子代理，主线程保持干净——派发话术锚点：用 Grep/Glob 扫整个仓库，列出所有引用 X 的文件:行号，不要改任何文件，只返回清单。派发判断（边界清晰就拆、纠缠留主线程）与 C1 评分闭环见 collab 模块。

重复的探索套路（梳理某模块调用链、找出所有 TODO）固化成 skill，下次一键复用。可抄最小骨架：

---
name: trace-callgraph
description: 梳理某符号/模块的调用链与影响面
---
# 步骤
1. Grep -n 搜目标符号所有引用
2. Glob 定位相关文件
3. Read offset/limit 读关键片段
4. 输出三栏：当前实现 / 调用方 / 波及范围

Skill 调用本身不算 explore_calls（不在 EXPLORE_TOOLS 桶）、不直接抬 A3；但调用 skill 后主线程仍会用 Grep/Read 落实探索，那些工具调用才抬 A3——杠杆是让"先探索后编辑"成为稳定默认流程。

7. 探索自检

逐条动手
  • ☐ 改之前让它先 Grep/Read 摸清影响面了？（动手：粘第 3 节骨架，看它回复里有没有"当前实现/调用方/波及范围"三栏）
  • ☐ explore_ratio 够不够高？（动手：跑 python mvp/score_session.py PATH.jsonl，看 A3 证据卡的 explore_calls / edit_calls）
  • ☐ 是精准 grep 还是倒整文件？（动手：看转录里 Read 调用带没带 limit，动辄读全文件就改 Grep -n 定位再分段 Read）
  • ☐ 工具箱够不够宽？（动手：跑 score_session.py 看 A3 证据卡的 distinct_tools，低于 10 就该用上 Glob/WebSearch/LS 等）
  • ☐ 大范围搜索该不该派子代理？（动手：任务是"扫全仓找 X"类就见 collab 模块 C1 话术）
  • ☐ shell 探索命令用上了吗？（动手：Bash 里 grep/rg/find/tree 也算 explore_calls，别只靠 Read 工具倒文件）
