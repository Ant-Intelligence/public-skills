A4 错误恢复与反 thrashing
"再试一次"不是调试,是碰运气。 thrashing 是 AI 编程特有的浪费:把同一句模糊提示反复丢给模型,不给新线索,它只能瞎猜——token 烧涨、越改越乱。给完整报错 + 假设 + 最小复现,缩小它的搜索空间,一次到位。

1. 为什么这项重要

低信息重试("还是不行""再改改")不给模型任何新信息,它只能基于上一轮的失败重新猜。更狠的是评分器把 thrash 量化成了占比:命中 thrash 占有效提示 ≥20% 就扣满 80 分,且这是加严后值——重试的代价比你想的大,且可量化、可跑分看到。

2. 反面 vs 正面

✗ 低信息重试(thrashing) 用户:给现有 auth 模块加登录功能,先看 src/auth/。
模型:[写了一大片]
用户:不对,再试一次。
模型:[又改了一大片]
用户:还是不行。
用户:又报错了。
——3 轮空转,每轮零新信息。"不对,再试一次""还是不行""又报错了"三条命中 is_thrash_prompt(thrash_count=3):"还是不行"命中 THRASH_PROMPT_RE 正则;"不对,再试一次""又报错了"因整条 ≤ 12 字符(THRASH_PROMPT_MAXLEN=12)被判为低信息重试。
✓ 带证据缩范围 第 1 轮 用户:登录报错 TypeError: Cannot read 'token' of undefined at validateToken (auth.js:42)。怀疑 token 为空——因为 401 时没存。先只在 auth.js:42 加 console.log(token),跑 npm test auth 复现,确认后再改,别大改。
第 1 轮 模型:已加日志,npm test auth 打印 undefined,假设确认。改 validateToken 加空值兜底,报错消失。
第 2 轮 用户:假设成立,报错已消失,提交吧。
——2 轮解决:搜索空间从"整个登录模块"缩到"auth.js:42 一行",thrash_count=0。

3. 照抄:带证据缩范围骨架

调试不靠文采,六个槽填齐,证据自然到位——直接粘进对话,按提示改:

# 带证据缩范围骨架(粘进对话,按提示填)
【完整错误栈】贴 TypeError / Error 全栈,别只贴一句话("报错了"不算)
【失败位置】文件:行号 + 函数名(如 auth.js:42 validateToken)——rg -n "validateToken" src/auth/ 定位
【我的假设 + 依据】"怀疑 token 为空,因为 401 时没存 token"——有依据,不是瞎猜
【最小复现步骤】先只在一处加日志 / 写最小复现,跑哪条命令复现(npm test auth)
【验收】日志打印出空值即确认;改完此行报错消失即完成
【约束】别大改,只动这一处,改完停给我看 diff

4. 四个可直接照做的动作

① 贴完整报错 + 失败位置

把完整错误栈、复现步骤、期望 vs 实际都给它,而不是一句"不行"。用 Grep 把报错关键串定位到文件:行号,贴给它——它就不用自己满仓库找。

报错如下(贴完整栈):TypeError at auth.js:42。
我用 Grep 查了,只有 validateToken 这一处读 token。
先别改,告诉我你认为原因是什么。

② 先假设,再动手

让它先说清"我认为原因是 X,依据是 Y",你认可假设后再让它改——把"试错"变成"验证假设",thrash 就没了。

先别动手。说清你认为根因是什么、依据是什么,我确认后你再改。

③ 缩小范围、最小复现

先加日志 / 写最小复现,把问题锁到一处,再修那一处,而不是全局大改。

先只在 auth.js:42 加 console.log(token),跑 npm test auth。
打印出来再决定怎么改,别大改。

这动的是哪个分

上面 ①②③④ 都在抬你的 A4（L1 错误恢复与反 thrashing）。公式 a4 = clamp(error_score − thrash_penalty)——两头都堵:thrash_penalty 按 thrash 占有效提示的比例抽分,占比到 20% 就扣满 80 分（THRASH_MAX_PENALTY=80、THRASH_RATIO_FULL=0.20,均为加严后值:原 40% 占比才扣满 40 分）;error_score 随工具错误率线性掉,error_rate ≥ 30% 直接归零（MAX_TOL_ERROR_RATE=0.30）——此时 a4 = clamp(0 − penalty) = 0,thrash 多寡都救不回来(error_rate 是地基,先把工具错误率压下去,A4 才有戏)。算笔账:effective_prompts = 20 时,4 条"还是不行"使 thrash_ratio = 0.20 → 扣满 80,A4 从 100 砸到 20;同样 4 轮换成带假设的实质提示,thrash_ratio = 0、penalty = 0,A4 守在 error_score。session 越大越关键——评分器故意用占比不用绝对次数(源码注释"避免绝对计数在大 session 上砸穿"),否则上万提示的会话 thrash 绝对数一大就砸穿到 0。thrash_count 是评分器内部量、对话里看不到——它靠 is_thrash_prompt 识别两类:命中 THRASH_PROMPT_RE(再试一次 / 重试 / 还是不行 / 继续 / try again / retry…)或整条提示 ≤ 12 字符（THRASH_PROMPT_MAXLEN=12）。跑 python mvp/score_session.py ~/.claude/projects/<hash>/<session-id>.jsonl,报告 A4 证据卡打出 thrash_count / thrash_ratio / tool_error_rate。A4 ∈ L1、层权重 0.25——与 A1 / A2 / A3 在 L1 层内平均后,再以 0.25 进总分。

④ 卡住两次就换思路

同一招连试两次没成,别再微调——让它退一步分析根因、换一个根本不同的方法,且每转一轮都在喂 thrash_count。

这招试两次没成,别再微调。退一步重新分析根因,换路:
· 2 次没成 → 换工具:从 Edit 退回 Read/Grep 重新定位
· 3 次没成 → 换层:从实现退回 spec/CLAUDE.md 读根因
· 仍卡     → 换子代理 或 /clear 重起主线
调试自检清单
  • ☐ 报错贴了完整栈 + 文件:行号了吗?(动手:把报错关键串用 rg -n "关键字" src/ 在仓库里定位,再贴给它)
  • ☐ 让它先讲清"原因假设 + 依据"了吗?(动手:粘「先别动手,说清根因和依据」这句触发话术)
  • ☐ 是最小复现锁定,还是全局大改?(动手:先只在一处加日志,跑最小复现命令确认假设)
  • ☐ 连试两次没成,换思路还是继续微调?(动手:连着两次同招没成,就让它退一步重新分析根因)
  • ☐ 这一轮提示是不是 thrash?(动手:提示 ≤ 12 字符或命中"还是不行 / 再试一次"就是 thrash,跑 python mvp/score_session.py PATH.jsonl 看 A4 证据卡的 thrash_count)
