协同、规则与知识沉淀

把个人效率变成团队能力：舍得拆、把规矩落成文件、改动进 git、经验写得下、过程留得住——对应 C1 / C2 / C4 / C5 / C6 五个域。

核心一句话：让别人（和三个月后的你）能接着用你今天的成果。 一个人用得溜是起点；能把套路沉淀成团队资产、把改动真正提交进仓库，才不会每次都从零开始。

不做这层，前面省的效率全散了

复杂任务不拆，主线程上下文迟早被细节撑爆；反复口头强调的规矩不落成文件，下次又得重讲一遍、新人又得踩一遍同样的坑；改了一堆不提交，一次 git reset 就等于白干；不留痕，事后想复盘什么都没有。这层不是可有可无的点缀——前面省下的效率能不能存下来全看它。

✗ 单打独斗、不留痕 复杂任务全堆主线程跑到上下文爆炸；规矩每次口头重申；改完不提交、不写说明，换个人完全接不上手。
✓ 协同 + 沉淀 复杂任务拆给子代理或独立 worktree；规矩写进 CLAUDE.md / hooks；改动及时进 git；关键决策落成文档。

复杂任务要舍得拆（C1）

主线程的上下文是稀缺资源。一个又大又杂的任务不拆，全塞在一个对话里，上下文很快被各种细节撑爆，模型开始忘事、串味。把边界清晰、能并行的子任务派给子代理（Agent / Task），主线程只收结论，保持干净。

判断标准很简单：这个子任务有没有清晰的输入输出边界？有，就拆出去；和别处纠缠、需要频繁来回沟通的，留主线程。并行多任务互不污染，可以各开一个独立 worktree（git worktree add 或 Claude Code 的 EnterWorktree）——注意不少项目约定只在明确需要时才用 worktree，别滥用。

评分上，C1 量的是你有没有真做子代理编排（subagent_calls + sidechain_events），进 L3；零编排只拿 10 分底分——协同域"不白给分"，要真拆职责才爬得上去。

反复讲的规矩，写成文件（C2）

一条规则你跟 AI 说了三遍以上——"别动评分公式""提交信息用 conventional commits""这个目录不许改"——别再口头重复了。写进 CLAUDE.md / AGENTS.md，或做成 hook 自动卡住，一次写、次次生效。

CLAUDE.md 会在会话启动时自动从项目根（及父目录）读进上下文，不用每次手贴；AGENTS.md 是跨工具通用的（Claude Code / Codex / Cursor 都读），团队混用工具时放它。最小模板：

# 项目约定
- 提交信息用 conventional commits（feat / fix / docs / ...）
- 打分器 mvp/score_session.py 是单文件、仅标准库，新增能力挂到现有函数
- 不要改评分公式/阈值（标准只在 docs/evaluation-system.md 附录 A）
- 测试：python -m unittest discover -s mvp/tests 必须离线全绿

# 常用路径
- 打分器：mvp/score_session.py
- 评分标准：docs/evaluation-system.md 附录 A
- 课件：learning-hub/<module>/index.html

口头的规矩一定会漂移，文件的不会。要更硬，就把规矩做成 hook——安全模块里的 block_secrets.py 拦密钥、验证模块里的 PostToolUse 自动跑测试，规矩就从"靠记性"变成"绕不过的机制"。评分上，C2 量的就是 rule_files（CLAUDE.md / AGENTS.md / .cursorrules 这类规则文件）存在与否，进 L3，一个都没有只有 20 分底分——注意打分器只认规则文件，hook 脚本是好实践但不计入 C2，想涨这分得写进 CLAUDE.md / AGENTS.md。

改动要进 git 才算数（C4）

"我改好了，在本地"——这不算交付。本地改动随时可能被覆盖、被重写、被一次误操作抹掉。进了版本库、提交了，才真正成为团队资产，也才能被后续的评分、校准、回溯用到。

可用的小步改动尽快提交，别攒一大坨；提交信息写清楚改了什么、为什么。评分上 C4 是产出主轴——git 可用时量的是 landed_ratio（真进提交的文件占比）；没 git 但转录里有 git commit 也能拿分（封顶 80）；既没 git 也没提交、只是碰过文件，封顶 55——评分不把"忙"当成"成"。

把经验写成能被搜到的东西（C5）

知识只在你脑子里，对团队等于不存在。一次踩坑的排查、一个模块的设计、一套环境的搭建——写成 spec、NOTES、README，放在团队能搜到的地方。写得不用漂亮，关键是有人能在你不在场时找到、看懂、照着做。

判断：这事下次还会有人问、有人做，就值得花十分钟写下来。C5 量的是 doc_files（有没有产出文档文件），进 L3；没写就是数据不足（None）。

留下过程，事后才回得来（C6）

只留最终代码，你丢掉的是"为什么这么决策""验证过哪些方案""踩过哪些坑"。这些在复盘、培训、排查时极其值钱——代码只告诉你是什么，过程才告诉你为什么。

计划、设计备选、验证结果、评审报告这类过程产物留下来、归好档。C6 量的是 thinking 比例、文件快照数、工具留痕——可回溯才得分，进 L3。Vibe Eval 这种评分体系本身就依赖过程留痕：没有原始 session 和报告，分数不可复核，coaching 也无从谈起。

沉淀自检
  • ☐ 复杂任务有清晰边界的部分，拆给子代理了吗？（C1）
  • ☐ 反复讲的规矩写进 CLAUDE.md / hooks 了吗？（动手：建一个 CLAUDE.md，先写 3 条最常重复的约定）（C2）
  • ☐ 改动提交进 git 了吗，还是堆在本地？（动手：git status 看有没有未提交的工作）（C4）
  • ☐ 这次的排查/设计经验值得写下来给别人复用吗？（C5）
  • ☐ 计划、验证、报告这些过程留痕了吗，事后回得来吗？（C6）
