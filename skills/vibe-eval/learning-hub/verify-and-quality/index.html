验证、质量与工程正确性

改完不验证，等于把"看着对"当成"真的对"。这一节讲怎么把改动真正验住、落地、不留暗坑——对应 B0 / B2 / B3 / B4 / B7 / B8 六个域，每条都说清「这动的是哪个分」。
B0 编辑落地B2 架构B3 验证闭环B4 正确性B7 契约B8 可观测性
核心一句话：没验证过的改动，不算完成。 AI 写得快，但"能跑"和"对"是两回事。验证就是把那层"看起来没问题"的皮揭开。

最坑的不是写崩，是静默故障

AI 提速之后，最坑的不是它写崩了——崩了你一眼就看见。最坑的是静默故障：代码能跑、测试能过、肉眼看没毛病，业务逻辑却是错的，上线才炸。这一类问题靠"再读一遍代码"挡不住，因为眼睛会自动补全你期望看到的东西。能挡住它的，只有验证手段——跑测试、跑构建、起服务看实际效果——把问题逼出来。

✗ 盲写不验证 "改好了。"——改完直接报完成，没跑测试、没起服务看效果。结果一个边界条件错了，到了测试同学手里才炸，返工还得从回忆里捞"当时改了啥"。
✓ 验证闭环 改完跑 npm test 和 npm run build，结果贴出来；前端改动起本地服务截张图；这个 bug 先写个能复现的失败测试再修，绿了才算完。

改完就验证（B3）

最低限度：改完让它把 test / lint / build 跑一遍，结果贴出来，别只说"应该没问题"。后端逻辑尤其别靠肉眼。

进阶做法是先红后绿：修 bug 之前，先写一个能复现这个 bug 的失败测试，看着它红，再改实现让它变绿。这样回归是被锁死的——下次谁改坏了，CI 立刻拦下来，不用等线上报警。这种"测试先行"的节奏，可以交给 tdd-guide 这类子代理或 skill 去盯，不用你每次嘴上强调。

你：改完直接 npm test && npm run build，把输出贴出来，红了我再看。

更高一档：把验证变成自动的（PostToolUse hook）

每次都靠嘴说"跑下测试"会忘。配一个 PostToolUse hook：Claude Code 每次 Edit/Write 之后自动跑你的测试，测试红了、失败信息回喂给它，它自己看见就会去修。等于把"改完就验证"从口号变成流程，你不用盯着提醒。

hook 脚本（放 .claude/hooks/run-tests-after-edit.py）：

import sys, json, subprocess
ev = json.load(sys.stdin)                       # 事件经 stdin 传入
path = (ev.get("tool_input") or {}).get("file_path", "")
if path.endswith((".md", ".txt")):              # 文档改动不触发测试
    sys.exit(0)
res = subprocess.run(["pytest", "-q"], capture_output=True, text=True)
if res.returncode != 0:
    sys.stderr.write(res.stdout + res.stderr)   # 失败原因打到 stderr
    sys.exit(2)                                  # 只有 exit 2 才回喂给 Claude

注册到 .claude/settings.json：

{
  "hooks": {
    "PostToolUse": [
      { "matcher": "Write|Edit",
        "hooks": [
          { "type": "command",
            "command": "python .claude/hooks/run-tests-after-edit.py",
            "timeout": 120 }
        ] }
    ]
  }
}

两个坑别踩：文件路径在 tool_input.file_path（从 stdin 的 JSON 里读），不是什么 $FILE_PATH 环境变量——网上不少老示例写错了，照抄拿不到路径；另一处更隐蔽——只有退出码 2 才会把 stderr 回喂给 Claude，其它非零码（包括 pytest 常用的 1）只显示给你、且反复失败会被禁用 hook。所以脚本得捕获 pytest 输出、失败时显式 sys.exit(2)，别让它落到文件末尾默默返回 0。

全量测试每次跑可能慢，按需收窄：快的先挡一道用 ruff check . && mypy src/（或 npm run lint && npm run typecheck）；只跑受影响的测试用 pytest -q tests/test_auth.py -x，文件名拿 git diff --name-only 的本次改动清单再喂给 pytest。

这动的是哪个分：B3 直接进你的能力分（L2 层，占总分权重最大）——它量的是你跑没跑 test/lint/build（浏览器 QA、IDE 诊断也算等价验证），改了却零验证会被直接打到 15 分，盲写重扣。

改了接口，别忘了调用方（B7）

翻车高发区：你让 AI 改了个函数签名、改了返回结构、改了字段名，它把那一处改得很漂亮——然后所有调用方全炸，因为它压根不知道还有谁在用。

改任何对外的东西之前，先让它 grep 出所有调用点、把影响面列给你，改完再让它挨个对一遍。改 schema 尤其要想清楚：这是兼容变更，还是破坏性变更？破坏性的，调用方一个都不能漏。

✗ 只改一处 把 getUser(id) 改成 getUser(userId)，参数名一改很"规范"，结果 17 个调用点还传 id，全挂。

打分上看，B7 量的是你有没有碰路由/schema/migration 这类契约面文件——它进 L2 能力分，但只是触达代理分，不是真在做契约一致性审计（那个得靠代码/OpenAPI 分析）。

看着对 ≠ 真的对（B4）

AI 最擅长写出"形似而神不似"的代码：变量名对、结构对、注释都对，但边界条件、空值、并发、时区这些地方悄悄错了。这种错你看代码看不出来，跑起来也不一定立刻暴露。

✗ 看着对，边界错 items[len(items)] 想取最后一个元素——happy path 下永远正常，空列表一来直接 IndexError。命名、结构都对，唯独边界没挡。

关键逻辑配测试，而且要覆盖边界，不只是 happy path。空输入、超长字符串、并发同时进来、跨年跨时区——只测正常输入的测试，约等于没有测试。

顺带说清：B4 这条当前不打分。代码对不对光看对话判断不了，系统诚实地标数据不足，不靠规则假装——所以这里的测试和边界覆盖，最终得靠你的测试套件和 CI 兜底。它不进分，但它决定你上线炸不炸。

出错了你得能定位（B8）

代码能跑，和"出问题时你能查"是两码事。最常见的暗坑：关键路径上既没日志、异常又被默默吞掉，线上炸了你打开日志两眼一抹黑，不知道哪一步出的。

关键路径（支付、鉴权、外部调用、状态变更）要留结构化日志、异常带上下文往外抛，坚决别 except: pass 或 logger.info('done') 这种没信息的：

# ✗ 吞掉、没信息
except Exception: pass
logger.info("done")
# ✓ 带上下文，出事能定位
logger.info("order %s paid amount=%s", order_id, amt)
raise ValueError(f"order {order_id} not found: status={order.status}")

结构化日志用 structlog / loguru，错误聚合接 sentry——这几个在 Python 里常见。这一条平时不显眼，出事的时候值千金：有日志你能五分钟定位，没日志你能查一晚上。

B8 同样是触达代理分：量你有没有碰 logger/异常/中间件/sentry 这类可观测面文件，进 L2；真实质量还得靠代码静态分析。

顺着项目结构走，别另起炉灶（B2）

AI 不知道你项目怎么分层，它默认按"通用最佳实践"来。可你项目大概率有自己的约定。结果它给你新建了一套并行的东西，和现有架构打架，后面维护的人想哭。

动手前先让它摸清家底：cat CLAUDE.md README.md、ls src/ 看分层；加新接口前让它读 package.json 和两三个现有 handler（比如 src/api/user_handler.py）照着模式写。一句话特别管用——"先找三个类似的现有实现，照着它们的模式写"，能挡掉一大半架构冲突。

B2 也一样——触达代理分，量你有没有碰 package.json/config/Dockerfile/模块入口这类结构配置文件，碰了才打分，没碰就是数据不足。

别光读不改（B0）

有种浪费很隐蔽：让 AI 探索、分析、出方案，来来回回聊了二十轮，最后一看 diff——空的。它一直在"准备动手"，从没真动手。

你：先别分析了，直接把方案落到 Edit 里，我看 diff。

别把"聊方案"当成产出，改到代码里才算这节没白做。每个阶段收尾时确认有实际的 Edit / Write 产出，别让整个会话在"讨论"里空转一场。

B0 最直接：它量你实际用编辑类工具（Edit/Write/MultiEdit）改了多少次——数次起步、十几次良好，进 L2。光读不改这域就低分；改没改到代码里，系统看得一清二楚。

交付前自检
  • ☐ 改完跑过 test / lint / build，结果贴出来了吗？（B3；动手：回看本会话有没有一条跑 pytest/npm test 且贴出输出的 Bash）
  • ☐ 有没有配 hook 或流程，让验证自动发生、不用每次嘴说？（B3）
  • ☐ 改了接口或数据结构，所有调用方都对上了吗？（B7；动手：让它 grep 改动的符号，数调用点）
  • ☐ 关键逻辑有测试，而且测了边界、不只是 happy path？（B4）
  • ☐ 关键路径有日志和错误处理，出问题能定位吗？（B8；动手：grep 本次改的文件里有没有 logger. / sentry capture）
  • ☐ 改动是顺着项目既有结构走的，没另起炉灶？（B2）
  • ☐ 探索和规划落到实际的 Edit/Write 了吗，还是在空转？（B0；动手：数本会话 Edit/Write 次数，<3 次多半还在空转）
